# Архитектура системы LawVision / LawRAG

> AI-платформа для поиска, анализа и создания правовых документов Республики Казахстан.
> Разработано лабораторией 306 КазНУ им. аль-Фараби. 2025–2026.

Документ описывает **архитектуру системы** и **как была обучена языковая модель**. Предназначен для защиты проекта.

---

## 1. Краткое описание

**LawVision** — это веб-платформа, которая делает казахстанское право доступным через искусственный интеллект. Пользователь задаёт вопрос на естественном языке (русском или казахском) и получает точный ответ со ссылкой на конкретный закон, статью и пункт.

Система объединяет **четыре функциональных модуля**:

| Модуль | Назначение |
|--------|-----------|
| 🤖 **Юридический ассистент (RAG)** | Вопрос-ответ по базе из 400+ правовых документов РК со ссылками на источники |
| 📜 **Генератор законопроектов** | Автоматическая генерация нормативных актов по стандартам РК (13 разделов, экспорт в PDF/DOCX/XLSX) |
| 📊 **Правовая аналитика** | Анализ массивов общественных комментариев: тематика, тональность, риски |
| 📑 **Конструктор договоров** | Генерация и анализ договоров, подписание ЭЦП (НУЦ РК) и якорение в блокчейне |

В основе лежат **две взаимодополняющие AI-стратегии**, описанные ниже.

## 2. Концепция: два подхода к ИИ

Ключевая особенность системы — мы используем **два разных способа** получения ответа от ИИ, потому что у каждого есть свои сильные стороны.

```
                          Вопрос пользователя
                                  │
              ┌───────────────────┴───────────────────┐
              ▼                                        ▼
   ┌────────────────────────┐            ┌──────────────────────────┐
   │   ПОДХОД 1: RAG         │            │  ПОДХОД 2: Fine-tuning    │
   │   (/chat)              │            │  (/chat-simple)           │
   ├────────────────────────┤            ├──────────────────────────┤
   │ Поиск по реальным      │            │ Дообученная модель        │
   │ документам + LLM        │            │ gemma-3n-4b-kazakh-law    │
   │                        │            │                          │
   │ • Ответ строго по базе  │            │ • Знания «зашиты» в веса   │
   │ • Ссылки на источники   │            │ • Быстрый ответ без поиска │
   │ • Нет галлюцинаций      │            │ • Специализирована на праве│
   └────────────────────────┘            └──────────────────────────┘
```

| | **RAG (Retrieval-Augmented Generation)** | **Fine-tuning (дообучение)** |
|---|---|---|
| **Откуда берётся ответ** | Из найденных в базе документов | Из «выученных» весов модели |
| **Главное преимущество** | Точность, проверяемость, ссылки на закон | Скорость, автономность, доменная лексика |
| **Главный риск, который снимает** | Галлюцинации ИИ (отвечает только по источникам) | Общая модель «плавает» в специфике права РК |
| **Когда обновляется знание** | Сразу — достаточно загрузить новый документ | Требует переобучения |

> **RAG — основной режим** платформы: он гарантирует, что ответ привязан к реальному документу.
> **Fine-tuning — дополнительный режим** для быстрых консультаций по типовым вопросам.

## 4. Как мы обучили модель (Fine-tuning)

В системе участвуют **две модели**, и важно их различать:

- **Эмбеддинг-модель** (`paraphrase-multilingual-MiniLM-L12-v2`) — используется **как есть**, в готовом (предобученном) виде. Мы её не обучали, а применяем для превращения текста в векторы.
- **Генеративная модель** (`gemma-3n-4b-kazakh-law`) — это модель, которую **мы дообучили сами** на казахстанском праве. Именно о ней идёт речь ниже.

### 4.1. Базовая модель

| Параметр | Значение |
|----------|----------|
| **Базовая модель** | Google **Gemma 3n**, ~4B параметров |
| **Тип дообучения** | Supervised Fine-Tuning (SFT) — обучение с учителем на парах «вопрос → эталонный ответ» |
| **Метод** | Parameter-Efficient Fine-Tuning (LoRA/QLoRA) — дообучаются только адаптеры, а не все 4 млрд весов, что позволяет уместить обучение на одной GPU |
| **Итоговое имя** | `gemma-3n-4b-kazakh-law` |
| **Домен** | Законодательство Республики Казахстан |

Мы взяли открытую модель Gemma 3n как «фундамент» (она уже умеет понимать русский и казахский языки) и **специализировали её под казахстанское право** — дообучили на размеченных юридических вопросах-ответах.

### 4.2. Обучающие данные

Датасет хранится в проекте в формате **JSONL**:

| Файл | Назначение | Размер |
|------|-----------|--------|
| `data/train.jsonl` | Обучающая выборка | **450 примеров** |
| `data/valid.jsonl` | Валидационная выборка (контроль качества) | **50 примеров** |

Каждый пример — это пара «**вопрос юриста / гражданина → эталонный экспертный ответ**» по реальным правовым процедурам РК (внесение изменений в кодексы, требования к документам, ответственность за нарушения и т.п.).

### 4.3. Формат данных (chat-шаблон Gemma)

Каждая строка датасета оформлена в **разметке диалога Gemma** — со специальными токенами, которые показывают модели, где реплика пользователя, а где — её собственный ответ:

```
<bos><start_of_turn>user
Какова процедура внесения изменений в Земельный кодекс
Республики Казахстан?<end_of_turn>
<start_of_turn>model
Процедура внесения изменений в Земельный кодекс РК начинается
с разработки проекта изменений уполномоченным государственным
органом... [полный эталонный ответ] ...<end_of_turn><eos>
```

- `<bos>` / `<eos>` — начало и конец примера;
- `<start_of_turn>user … <end_of_turn>` — вопрос;
- `<start_of_turn>model … <end_of_turn>` — эталонный ответ, который модель учится воспроизводить.

Благодаря такому формату модель учится не просто «продолжать текст», а **отвечать в диалоговом режиме** именно на юридические вопросы.

### 4.4. Процесс обучения

```
   400+ правовых        ручная / экспертная        размеченный
   документов РК   ─►   подготовка Q&A       ─►    датасет (JSONL)
                        пар по процедурам          train + valid
                                                        │
                                                        ▼
   Gemma 3n 4B    ─►   SFT (LoRA/QLoRA)        ─►   gemma-3n-4b-
   (базовая)           обучение на GPU              kazakh-law
                       + валидация                 (готовая модель)
```

1. **Сбор материала** — на основе действующей базы правовых документов РК подготовлены вопросы и эталонные ответы.
2. **Разметка** — каждый пример приведён к chat-шаблону Gemma и разделён на обучающую и валидационную выборки.
3. **Дообучение (SFT)** — базовая Gemma 3n дообучается методом LoRA/QLoRA: модель прогоняет примеры, сравнивает свой ответ с эталоном и корректирует адаптеры.
4. **Контроль качества** — на валидационной выборке (50 примеров) проверяется, что модель не «переобучилась» и обобщает знания.
5. **Упаковка** — обученные веса сохраняются как `gemma-3n-4b-kazakh-law`.

> **Примечание.** Сам тренировочный конвейер вынесен в отдельный проект (`fine_tune_llm_2222`). В данном репозитории находятся **обучающие данные** (`data/train.jsonl`, `data/valid.jsonl`) и **клиент** для использования готовой модели.

### 4.5. Развёртывание обученной модели

Готовая модель поднимается как **отдельный микросервис** с HTTP API, а основное приложение обращается к нему через провайдер:

```
Flask (app) ──HTTP──► Fine-tuned API (:8000)
                      • POST /ask     → {question, max_tokens, temperature, top_p}
                      • GET  /health  → {model_loaded: true/false}
```

Код-обёртка — [llm_providers/finetuned_provider.py](llm_providers/finetuned_provider.py). Если сервис недоступен, система **автоматически продолжает работать** на других провайдерах (graceful degradation).

## 5. RAG-конвейер (основной режим)

RAG (Retrieval-Augmented Generation) — это «поиск + генерация». Вместо того чтобы выдумывать ответ, модель **сначала находит** нужные фрагменты в реальных документах, а **потом формулирует** ответ на их основе со ссылками.

```
┌──────────── ИНДЕКСАЦИЯ (выполняется заранее, при загрузке документов) ───────────┐
│                                                                                  │
│  Документ (.txt/.pdf) ─► очистка текста ─► разбивка на чанки                      │
│                                            (1000 симв., overlap 200,             │
│                                             по границам предложений)              │
│                                                   │                              │
│                                                   ▼                              │
│                          Embeddings (MiniLM-L12, 384-мерный вектор)              │
│                                                   │                              │
│                                                   ▼                              │
│                          PostgreSQL: document_chunks.embedding (Vector 384)      │
└──────────────────────────────────────────────────────────────────────────────────┘

┌──────────── ЗАПРОС (в реальном времени) ─────────────────────────────────────────┐
│                                                                                  │
│  Вопрос ─► вектор вопроса ─► ГИБРИДНЫЙ ПОИСК                                       │
│                              ├─ семантический (pgvector, косинусное расстояние)   │
│                              └─ по ключевым словам (пересечение слов)             │
│                                       │                                          │
│                              объединение + взвешивание + дедупликация             │
│                                       │ (top-5 чанков)                           │
│                                       ▼                                          │
│  Сборка контекста с пометками [Источник 1], [Источник 2]...                       │
│                                       │                                          │
│                                       ▼                                          │
│  LLM (Ollama gpt-oss:20b) генерирует ответ строго по контексту                   │
│                                       │                                          │
│                                       ▼                                          │
│  Ответ + список источников + оценка уверенности (confidence)                      │
└──────────────────────────────────────────────────────────────────────────────────┘
```

### 5.1. Индексация документов — [embeddings/processor.py](embeddings/processor.py)

- Поддержка форматов `.txt` и `.pdf` (через pdfplumber).
- **Чанкинг:** текст режется на фрагменты по ~1000 символов с перекрытием 200 символов; границы выравниваются по концам предложений, чтобы не разрывать мысль.
- **Векторизация:** каждый чанк превращается в 384-мерный вектор моделью `paraphrase-multilingual-MiniLM-L12-v2`.
- **Хранение:** векторы кладутся в PostgreSQL в колонку типа `Vector(384)` (расширение pgvector).
- **Офлайн-режим:** модели грузятся только из локального кеша (`HF_HUB_OFFLINE=1`) — данные не уходят в облако.

### 5.2. Гибридный поиск — [rag/retriever.py](rag/retriever.py)

Объединяет два метода, чтобы повысить точность:

| Метод | Как работает | Сила |
|-------|-------------|------|
| **Семантический** | Косинусное расстояние между векторами (`embedding.cosine_distance` в pgvector) | Находит по смыслу, даже если слова другие |
| **По ключевым словам** | Пересечение слов запроса и текста чанка | Ловит точные термины, номера статей |

Результаты **объединяются с весами** (семантика — основной вес, ключевые слова дают бонус), затем выполняется **дедупликация** перекрывающихся фрагментов (>50% перекрытия позиций отбрасывается). На выход — top-5 наиболее релевантных чанков.

### 5.3. Генерация ответа — [rag/generator.py](rag/generator.py)

- Найденные чанки собираются в контекст с маркерами `[Источник N]`.
- LLM получает **строгий системный промпт**: отвечать на языке вопроса (RU/KZ/EN), указывать источники, не выходить за рамки права, не раскрывать базовую модель (представляться как «LawVision, созданный лабораторией 306 КазНУ им. аль-Фараби»).
- Считается **оценка уверенности** (confidence) на основе числа и качества найденных источников.
- Если релевантных документов не найдено — модель честно об этом сообщает и отвечает из общих знаний с пометкой.

Низкая `TEMPERATURE = 0.1` сделана специально — для **точности и предсказуемости** ответов (минимум «фантазии»).

## 6. Модель данных (PostgreSQL + pgvector) — [database/models.py](database/models.py)

Система мигрировала с SQLite на **PostgreSQL** с расширением **pgvector** для нативного векторного поиска. Доступ — через **SQLAlchemy ORM** с пулом соединений.

| `users` | Пользователи/администраторы |

## 7. Функциональные модули

### 7.1. Юридический ассистент (RAG) — `rag/`
Главный модуль (раздел 5). Чат с поиском по базе 400+ документов и ответами со ссылками на закон.

### 7.2. Генератор законопроектов — `law_generator/`
По описанию инициативы автоматически формирует нормативный акт по стандартам РК: пояснительная записка, текст закона, финансово-экономическое обоснование, оценка регуляторного воздействия, антикоррупционная экспертиза, сравнительная таблица и др. (13 разделов). Включает **валидатор** структуры и **экспорт** в PDF / DOCX / XLSX ([law_generator/export.py](law_generator/export.py)).

### 7.3. Правовая аналитика — `legal_analytics/`
Обрабатывает массивы общественных комментариев к законопроектам: классификация по темам, определение тональности (поддержка / критика / нейтрально), выявление рисков, ML-инсайты и интерактивный дашборд ([legal_analytics/analyzer.py](legal_analytics/analyzer.py), [legal_analytics/dashboard.py](legal_analytics/dashboard.py)).

### 7.4. Конструктор договоров — `contracts/`
Генерация и юридический анализ договоров **10 типов** (купля-продажа, аренда, услуги, поставка, заём, NDA, трудовой, агентский, подряд и др.). Ключевая особенность — **юридически значимое подписание**:

```
Договор ─► хеш документа (SHA-256)
              │
              ▼
   ЭЦП через NCALayer (НУЦ РК)  ──► PKCS#7-конверт
              │                      проверка: contracts/signature_verifier.py
              ▼                      (парсинг сертификата, извлечение ИИН)
   Якорение в блокчейне (Web3)
   смарт-контракт ContractAnchor.sol:
   anchor(docHash, signersHash, signatureCount, pkcs7Hash)
              │
              ▼
   Публичная проверка подлинности по /verify
```

- **ЭЦП:** интеграция с **NCALayer** (национальная система электронной подписи РК), подпись в формате PKCS#7, проверка сертификата и извлечение ИИН подписанта — [contracts/signature_verifier.py](contracts/signature_verifier.py).
- **Блокчейн:** хеш подписанного документа записывается в смарт-контракт `ContractAnchor` (Solidity) через Web3 — [contracts/blockchain.py](contracts/blockchain.py), [contracts/chain/ContractAnchor.sol](contracts/chain/ContractAnchor.sol). Это даёт **неизменяемое доказательство** факта и времени подписания.
- **Проверка:** любой может проверить подлинность договора по странице `/verify`, не имея доступа к самому документу.
- Реализован **graceful degradation**: при отключённом блокчейне (`BLOCKCHAIN_STUB`) или офлайн-проверке ЭЦП система остаётся работоспособной для демонстрации.

## 8. AI-слой: модульность провайдеров — `llm_providers/`

Языковые модели подключаются через **фабрику провайдеров** ([llm_providers/factory.py](llm_providers/factory.py)) — это позволяет **менять модель без переписывания кода**.

```
LLMProviderFactory.create_provider(type)
        │
        ├─ 'ollama'    → OllamaProvider   (основной, локальный: gpt-oss:20b)
        ├─ 'finetuned' → FineTunedProvider (наша модель: gemma-3n-4b-kazakh-law)
        └─ 'openai'    → OpenAIProvider   (deprecated, облачный)
```

Все провайдеры реализуют единый интерфейс `LLMProvider` (метод `chat_completion`). Благодаря этому:
- **по умолчанию всё работает локально** (Ollama) — данные не покидают сервер, что критично для гос. сектора;
- можно в любой момент **подключить более мощную модель** без переработки системы.

## 10. Безопасность и приватность

- **Локальная обработка** — основной LLM (Ollama) работает на сервере; конфиденциальные документы не уходят в облако.
- **Защита от галлюцинаций** — RAG-режим отвечает только по реальным документам со ссылками.
- **Анонимизация** — IP-адреса в аналитике хешируются (SHA-256).
- **Админ-панель** — скрыта из навигации, защищена логином/паролем (Flask session).
- **Секреты** — в `.env`, вне системы контроля версий.
- **Юридическая значимость** — ЭЦП НУЦ РК (PKCS#7) + блокчейн-якорение для договоров.
- **Шифрование трафика** — Cloudflare SSL от браузера до сервера.

## 12. Итог: чем сильна архитектура

1. **Два AI-подхода** — RAG для точности и проверяемости + дообученная модель для скорости и доменной специфики.
2. **Защита от галлюцinaций** — каждый ответ привязан к реальному документу со ссылкой на закон.
3. **Двуязычность** — русский и казахский без потери качества.
4. **Локальность данных** — обработка на собственном сервере, критично для гос. органов.
5. **Модульность** — LLM-провайдеры, типы договоров, модули заменяются и расширяются без переработки ядра.
6. **Масштабируемость** — новые документы индексируются без изменения кода; подход применим к праву любой страны.
7. **Юридическая значимость** — ЭЦП НУЦ РК и блокчейн-якорение придают документам доказательную силу.
