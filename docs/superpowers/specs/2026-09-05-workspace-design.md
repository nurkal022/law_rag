# Рабочее место юриста: персональные документы и дела

**Дата:** 2026-09-05
**Ветка:** `version4redisign` (от `origin/server-local`, `fd32455`)
**Статус:** дизайн утверждён, готов к планированию реализации

---

## 1. Задача

Все четыре модуля LawVision — RAG-ассистент, генератор законопроектов, правовая
аналитика, конструктор договоров — сегодня работают без состояния. Пользователь
генерирует договор, и договор исчезает. Загружает PDF в чат — файл нигде не
сохраняется, в базе остаётся только текст переписки. Персистентность есть лишь у
законопроектов (`LawProject` и его версии).

Из-за этого к вчерашней работе нельзя вернуться, и ни юрист, ни госслужащий, ни
компания не могут пользоваться системой всерьёз.

Виток добавляет недостающий слой: библиотеку персональных документов, объединение
их в дела и диалог с собственным документом, опирающийся на нормы РК.

**Аудитория:** все сегменты сразу — юристы, госслужащие, бизнес, граждане.
**Горизонт:** несколько недель.
**Вне рамок:** перенос модуля опросов из `main` и ЭЦП/блокчейн-верификации из
`feat/contracts-redesign` — обе ветки в этот виток не входят.

---

## 2. Ключевая граница

Таблицы `documents` и `document_chunks` — это корпус НПА: около 400 общих
документов, по которым ищет RAG.

**Пользовательские файлы в эти таблицы не попадают ни при каких условиях.** Иначе
чужой договор окажется в выдаче по правовому вопросу и отравит ответы всем
пользователям.

Персональные документы живут в отдельном пространстве таблиц с той же механикой
pgvector и той же моделью эмбеддингов.

### `user_document_versions` — история версий

| Поле | Тип | Примечание |
|---|---|---|
| `id` | Integer PK | |
| `user_document_id` | FK, cascade delete | |
| `version_no` | Integer | последовательный, с 1 |
| `storage_path` | String(512) | файл этой версии |
| `note` | Text | nullable, комментарий к версии |
| `created_at` | DateTime | |

Уникальность: `(user_document_id, version_no)`.

**Когда создаётся версия.** Ровно в двух случаях, и ни в каких других:

1. Пользователь загружает файл в существующий документ через «Загрузить новую
   версию». Прежний файл остаётся как версия, новый становится текущим.
2. Модуль договоров или законопроектов перегенерирует документ, уже сохранённый в
   библиотеке.

Обычная загрузка нового файла версию не создаёт — она создаёт новый документ.
Версия 1 заводится вместе с документом, чтобы исходный файл всегда был доступен.
Переиндексация после смены версии обязательна: чанки старой версии удаляются
вместе с ней.

### Изоляция

Каждая выборка фильтруется по `user_id`; чанки достаются только через join к
своему документу. Это единственный способ доступа к данным, а не дополнительная
проверка поверх общего запроса — иначе рано или поздно один из запросов её
пропустит.

## 4. Хранилище файлов

Файлы лежат на диске: `uploads/<user_id>/<uuid>.<ext>`, том монтируется в
`docker-compose.yml` как `./uploads:/app/uploads` — по образцу уже существующих
`./docs` и `./exports`.

Не в базе: `bytea` раздует Postgres и сломает нынешнюю схему бэкапов
(`scripts/backup.sh`).

Имя файла на диске — UUID; исходное имя хранится только в БД.

## 5. Приём и индексация документа

### Пайплайн загрузки

`POST /api/workspace/documents` (multipart):

1. Проверка расширения (PDF, DOCX) и размера — лимит `WORKSPACE_MAX_FILE_MB`
2. Подсчёт `sha256`; при совпадении с существующим документом пользователя —
   возврат этого документа без создания дубля
3. Сохранение в `uploads/<user_id>/<uuid>.<ext>`
4. Извлечение текста: `pdfplumber` для PDF, `python-docx` для DOCX — обе
   зависимости уже установлены
5. Создание `UserDocument` со `status='pending'` и **немедленный ответ клиенту**
6. Чанкование и эмбеддинги — в фоновом потоке

### Снятие нынешних ограничений

Существующий `/api/chat/upload` ([app.py:457](../../../app.py)) обрезает PDF на
30 странице и текст на 8000 символах, потому что весь текст уходит одним куском в
промпт. В библиотеке эти лимиты не нужны: документ хранится целиком, а в промпт
попадают только релевантные чанки. Договор на 60 страниц перестаёт обрываться на
середине.

### Фоновая индексация

Daemon-поток с явным `app_context()` — тот же приём, что уже применён для
авто-инициализации RAG ([app.py:399](../../../app.py)). Celery, Redis и очередь
задач не вводятся: на текущем масштабе это лишний слой инфраструктуры.

Цена решения и как она закрывается. Gunicorn запущен с `--max-requests 500`
(Dockerfile), воркеры регулярно перезапускаются, и их всего два — поток с
индексацией может погибнуть на середине:

- чанки пишутся одной транзакцией в конце, наполовину проиндексированного
  документа не бывает;
- документ, висящий в `pending` дольше `WORKSPACE_PENDING_TIMEOUT_MIN` (15 минут),
  при следующем открытии библиотеки переводится в `failed`;
- у `failed` в интерфейсе есть кнопка «Переиндексировать» — тот же путь, что при
  первичной загрузке;
- недоступность эмбеддинг-сервера — это `failed` со внятной причиной, а не 500-я
  ошибка: документ уже сохранён и читается, он лишь не участвует в поиске.

### Чанкование

Переиспользуется `split_into_chunks` из
[embeddings/processor.py](../../../embeddings/processor.py) с теми же
`CHUNK_SIZE=1000` и `CHUNK_OVERLAP=200`, что у корпуса НПА.

Одинаковая нарезка и одна модель BGE-M3 с обеих сторон — обязательное условие для
перекрёстных ссылок (раздел 6): сопоставлять можно только векторы из одного
пространства.

### Автоматическое пополнение библиотеки

Договоры и законопроекты попадают в библиотеку при генерации, со `source='contract'`
и `source='law_project'`, минуя загрузку файла — текст уже есть в системе. Именно
это делает библиотеку местом, где сходятся все четыре модуля, а не пятой
изолированной функцией.

## 6. Диалог с документом

### Двойное извлечение

Запрос идёт в два индекса одновременно:

- чанки пользовательского документа, отфильтрованные по `user_id` и выбранному
  документу либо делу;
- корпус НПА через существующий `hybrid_search` из
  [rag/retriever.py](../../../rag/retriever.py).

В промпт они попадают **раздельными, явно помеченными блоками**: «ФРАГМЕНТЫ ВАШЕГО
ДОКУМЕНТА» и «НОРМЫ ЗАКОНОДАТЕЛЬСТВА РК». Без этой границы модель выдаёт условие
из договора за требование закона.

### Малые документы

Если в документе меньше `WORKSPACE_SMALL_DOC_CHUNKS` (12 чанков, около 12 тысяч
знаков — типичный договор), извлечение по нему пропускается и текст идёт в промпт
целиком. Поиск по документу из восьми абзацев только теряет контекст. Индексация
всё равно выполняется — она нужна для поиска по всей библиотеке.

### Перекрёстные ссылки «пункт → норма»

Сегодня `ContractAnalyzer._legal_context`
([contracts/analyzer.py](../../../contracts/analyzer.py)) ищет нормы по запросу,
собранному **только из типа договора**: «договор поставки обязательные условия
ответственность сторон…». Текст документа в поиск не попадает, поэтому для любого
договора поставки достаётся один и тот же набор норм.

Новый механизм ищет **от текста конкретного пункта**: для
`WORKSPACE_CROSSREF_CHUNKS` (по умолчанию 3) наиболее релевантных чанков документа
каждый чанк сам становится запросом к корпусу НПА. Получается привязка «ваш пункт → норма», из
которой модель делает вывод вида: «пункт 7.2 устанавливает неустойку 5% в день, при
том что статья 297 ГК РК позволяет суду уменьшить явно несоразмерную неустойку».

Цена: столько же дополнительных векторных поисков на запрос, сколько взято чанков.
Поэтому число вынесено в конфиг, а не зашито.

### Два режима

- **Вопрос по документу** — свободный запрос, извлечение ведёт вопрос. Основной
  сценарий.
- **Проверка документа** — систематический разбор по пунктам. Второй анализатор не
  пишется: переиспользуется `ContractAnalyzer`, которому передаётся готовый
  контекст норм. Одна правка в `_legal_context` — принимать переданный контекст
  вместо самостоятельного поиска по типу договора — улучшает заодно и существующую
  страницу договоров.

### История диалога

Диалог привязывается к документу или делу, а не к анонимной сессии, как сейчас в
`ChatHistory` через `session_id`. Существующая таблица не заменяется — в неё
добавляются две nullable-колонки: `user_document_id` и `matter_id`.

### Поиск по библиотеке

Семантический поиск сразу по всем своим документам, отдельно от диалога — отвечает
на вопрос «в каком договоре был пункт об арбитраже в Лондоне». Практически бесплатен:
индекс уже построен.

## 8. Интерфейс

Три экрана в существующем стиле (Jinja + Bootstrap):

- `/workspace` — библиотека: список документов, фильтр по делу, статус индексации,
  загрузка перетаскиванием, поиск по своим документам
- `/workspace/matters/<id>` — дело: входящие документы, описание, история диалогов
- `/workspace/documents/<id>` — документ: текст слева, диалог справа; ссылки на
  нормы в ответе кликабельны и открывают фрагмент НПА

В навигации появляется «Мои документы», видимый только залогиненным. Гостю на месте
кнопки загрузки показывается предложение войти — естественная точка конверсии из
пятивопросного триала в регистрацию.

## 9. Миграция схемы

Схема создаётся через `db.create_all()` при старте ([app.py:380](../../../app.py));
Alembic в проекте не подключён, изменения существующих таблиц делаются разовыми
скриптами в `scripts/`.

- Четыре новые таблицы появятся сами через `create_all()`.
- Две nullable-колонки в `chat_history` `create_all()` **не добавит** — он не
  трогает существующие таблицы. Нужен идемпотентный
  `scripts/migrate_workspace_tables.py` с `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`,
  по образцу [scripts/migrate_embeddings_1024.py](../../../scripts/migrate_embeddings_1024.py).

Без этого скрипта деплой на сервер сломает чат: модель ждёт колонки, которых в базе
нет.

## 10. Ограничения

Всё выносится в `config.py`:

| Параметр | Значение | Смысл |
|---|---|---|
| `WORKSPACE_MAX_FILE_MB` | 20 | размер одного файла |
| `WORKSPACE_MAX_DOCS_PER_USER` | 100 | документов на пользователя |
| `WORKSPACE_MAX_STORAGE_MB` | 500 | суммарный объём на пользователя |
| `WORKSPACE_MAX_CONCURRENT_INDEXING` | 5 | одновременных индексаций на приложение |
| `WORKSPACE_PENDING_TIMEOUT_MIN` | 15 | до перевода в `failed` |
| `WORKSPACE_SMALL_DOC_CHUNKS` | 12 | порог «маленького» документа |
| `WORKSPACE_CROSSREF_CHUNKS` | 3 | чанков для перекрёстного поиска |

Предел одновременных индексаций существенен: эмбеддинг-сервер общий с корпусом НПА,
и очередь тяжёлых пользовательских документов не должна ронять основной чат.

Превышение любого лимита — понятное сообщение пользователю, а не 500-я ошибка.

## 11. Безопасность

Три пункта, которые легко упустить и дорого чинить потом:

1. **Путь к файлу никогда не приходит из запроса.** Файл отдаётся только по `id`
   документа с проверкой владельца. Имя на диске — UUID. Так закрывается path
   traversal.
2. **Загруженный PDF не рендерится в браузере из нашего домена** — отдаётся с
   `Content-Disposition: attachment`. PDF со скриптом иначе получает доступ к сессии
   пользователя.
3. **Удаление документа удаляет и файл с диска, и чанки.** Иначе за месяц накопится
   мусор, который никто не найдёт.

## 12. Тестирование

Тестов в проекте нет, pytest не в зависимостях. Полный набор с нуля в этот виток не
помещается. Подключается pytest и покрываются три места, где ошибка не видна глазами
и стоит дорого:

1. **Изоляция по пользователю** — запрос чужого документа, чужого дела, чужих чанков
   в поиске. Ошибка здесь означает утечку клиентского договора и внешне не проявляется
   никогда.
2. **Дедупликация и чанкование** — повторная загрузка не создаёт дубль; границы
   чанков не теряют текст на стыках.
3. **Деградация индексации** — эмбеддинг-сервер недоступен: документ сохранён, статус
   `failed`, приложение продолжает отвечать.

Интерфейс, экспорт и качество диалога проверяются вручную — при таком горизонте это
дешевле.

## 13. Сознательно вне рамок

Каждый пункт — логичное продолжение, но отдельный виток:

- совместный доступ к делам между пользователями;
- комментарии и аннотации на документе;
- OCR отсканированных документов;
- сравнение двух версий документа с подсветкой различий;
- полнотекстовый поиск по библиотеке помимо семантического.
