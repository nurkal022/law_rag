## 0. Что есть сейчас и почему это «сырое»

Диагноз по коду, не по ощущениям.

### Договоры (`contracts/`, 1 540 строк)
- **Девять типов** в `contracts/templates.py`: купля-продажа, аренда, услуги, трудовой, займ, поставка, подряд, конфиденциальность, агентский. У каждого 6 общих полей (стороны, ИИН/БИН, адреса, город, дата) плюс 4–8 специфичных, список разделов и строка «правовая основа».
- **Генерация — один вызов LLM** (`contracts/generator.py:14`): системный промпт со списком разделов, данные полей в тексте, `temperature 0.2`, `max_tokens` из конфига. На выходе **markdown-строка**. Никакой структуры: нельзя адресовать «пункт 4.2», нельзя проверить, что существенные условия на месте.
- **Ничего не сохраняется.** Модели `Contract` в БД нет. Договор живёт в памяти вкладки; закрыл — потерял. Отсюда же невозможность «дописать промптом»: нечего дописывать.
- **Экспорт** (`contracts/exporter.py`): клиент отправляет markdown обратно на сервер, тот парсит его регулярками в `python-docx` или `reportlab`. Форматирование зависит от того, как именно модель расставила `#` и `**`. Стилей документа нет: ни поля, ни нумерации, ни таблицы реквизитов, ни блока подписей как объекта.
- **Анализ** (`contracts/analyzer.py`) — рабочий, с позицией стороны и RAG-контекстом. Его оставляем, но переносим в новый UI.
- **Фронт** (`ContractsPage.tsx`, 827 строк + `data.ts`, 1 881 строка) — целиком на моках, к API не подключён.

### Законопроекты (`law_generator/`, 2 500 строк)
- Сильнее договоров: 13 разделов (титул, аннотация, пояснительная записка, текст, сравнительная таблица, финансовое обоснование, АРВ, акт соответствия, антикоррупционная экспертиза, прогноз, глоссарий, машиночитаемое приложение, журнал), модели `LawProject` / `LawProjectVersion` / `LawGenerationSession`, валидатор с подсказками по полям.
- **Генерация — 13 последовательных вызовов LLM** внутри одного HTTP-запроса. Это минуты ожидания без прогресса; на проде запрос отвалится по таймауту прокси.
- **Экспорт**: txt / json / html / pdf через `reportlab` с самодельным парсером markdown, пишет временные файлы на диск. **Нет DOCX, нет XLSX**, хотя половина разделов — таблицы.
- Итерации нет: версия создаётся, но перегенерировать раздел с уточнением нельзя.
- **Фронт** (`LawsPage.tsx`, 746 строк) — моки, мастер не подключён к сессиям.

### Документы (`workspace/`)
- Спецификация написана и утверждена (`2026-09-05-workspace-design.md`): таблицы `matters`, `user_documents`, `user_document_versions`, `user_document_chunks`, жёсткая граница «пользовательские файлы не попадают в корпус НПА».
- **Бэкенда нет вообще.** Три экрана на фронте (`LibraryPage`, `DocumentPage`, `MattersPage`) — моки.

### Общее для всех трёх
- Стриминг ответа выключен (`"stream": False` в `llm_providers`).
- 75 вызовов `print()` вместо `logging`; ограничения частоты запросов нет; тестов нет.
- Три модуля решают одну и ту же задачу — «сгенерировать структурированный юридический документ, дать его править и скачать» — тремя несовместимыми способами.

**Главный вывод:** чинить каждый модуль по отдельности — значит трижды написать одно и то же. Сначала строим общий **документный движок**, потом сажаем на него договоры, законопроекты и библиотеку.

## 1. Документный движок (общий фундамент)

Один пакет `docengine/` на бэкенде. Им пользуются все три модуля.

### 1.1 Структура документа вместо markdown-строки

Любой сгенерированный документ хранится как дерево, а не как текст:

```
Document
  meta: { kind: contract|law_project|user_doc, type_id, lang, title, created, parties[] }
  requisites: { party1: {...}, party2: {...}, city, date, number }
  sections[]:
    { no: "1", title: "Предмет договора",
      clauses[]: { no: "1.1", text: "...", refs: ["ГК РК ст. 406"] } }
  tables[]: { id, title, columns[], rows[][] }       # для законопроектов
  annexes[]: { title, sections[] }
  signatures: { party1: {...}, party2: {...} }
```

Что это даёт сразу:
- **Адресуемость.** «Измени пункт 4.2» — это операция над узлом, а не поиск подстроки в markdown.
- **Проверяемость.** После генерации движок сверяет: все ли обязательные разделы на месте, все ли существенные условия заполнены, нет ли пустых пунктов.
- **Один рендерер для всех форматов.** HTML-предпросмотр на экране, DOCX, PDF и XLSX собираются из одного дерева, поэтому «как на экране, так и в файле».
- **Диффы версий** по пунктам, а не по строкам.

LLM просим отвечать **строго в этой JSON-схеме** (structured output / JSON mode у провайдера, с валидацией pydantic и одной повторной попыткой при невалидном ответе).

### 1.2 Генерация по разделам, а не одним куском

Длинный договор (подряд, поставка с приложениями) или законопроект не помещается в один ответ модели без потери качества в конце. Движок:
1. Строит **план** документа из паспорта типа (разделы, обязательные пункты).
2. Генерирует **разделы по очереди**, передавая уже готовые как контекст, чтобы нумерация и термины сходились.
3. Между разделами отдаёт прогресс клиенту (SSE): «Раздел 4 из 11: Ответственность сторон».
4. В конце — проход проверки (п. 1.1) и, при необходимости, точечная догенерация.

Генерация выносится в **фоновую задачу** (очередь на PostgreSQL через `SELECT ... FOR UPDATE SKIP LOCKED`, без Redis и Celery, как уже решено в спецификации рабочего места), а HTTP-запрос возвращает `job_id`. Клиент подписывается на SSE-поток прогресса. Обрыв соединения не убивает генерацию.

### 1.3 Версии и итерации промптом

Единая модель для всех видов:

```
documents            id, kind, type_id, owner_id, matter_id?, title, lang, status, created_at
document_versions    id, document_id, no, tree (JSONB), summary, created_by (user|llm), created_at
document_turns       id, document_id, version_from, version_to, role (user|assistant),
                     text, ops (JSONB), created_at
```

Каждое «дополни промптом» — это `document_turn`: пользователь пишет запрос, движок отдаёт LLM **текущее дерево + запрос**, получает **список операций**, а не новый документ целиком:

```
ops: [
  { op: "replace_clause", no: "4.2", text: "..." },
  { op: "insert_section", after: "6", title: "...", clauses: [...] },
  { op: "delete_clause", no: "7.3" },
  { op: "set_requisite", path: "party2.bank", value: "..." }
]
```

Операции применяются к дереву → новая версия. Так модель не может «случайно потерять» половину документа, а пользователь видит ровно то, что изменилось, пункт за пунктом, с возможностью откатить любую версию.

Типовые быстрые команды (кнопки над полем ввода): «Ужесточить в пользу стороны 1 / 2», «Добавить штрафные санкции», «Упростить язык», «Перевести на казахский», «Добавить приложение: акт приёма-передачи». Плюс **ручная правка** любого пункта прямо в предпросмотре: она тоже создаёт версию с `created_by: user`.

### 1.4 Рендер и экспорт

Один HTML-шаблон на вид документа (`docengine/render/contract.html`, `law_project.html`), из него:
- **Предпросмотр** на экране: тот же HTML внутри «листа A4», шрифт Times New Roman 12, поля 20 мм, как в юридической практике РК.
- **PDF**: WeasyPrint из того же HTML (уже в зависимостях, `weasyprint==60.2`). `reportlab` и самодельный парсер markdown удаляем.
- **DOCX**: `python-docx` по дереву, а не по markdown: настоящие стили заголовков, многоуровневая нумерация Word, таблица реквизитов, блок подписей таблицей в две колонки, колонтитул с номером страницы и названием документа. Файл-шаблон `docengine/render/base.docx` со стилями, чтобы юрист мог открыть и править в Word без потери форматирования.
- **XLSX**: `openpyxl` (добавить в зависимости) для табличных разделов: сравнительная таблица, финансовое обоснование, глоссарий, спецификация к договору поставки, график платежей к займу/аренде.
- **ODT** и **Markdown** — не делаем. Не просили, юристы РК работают в Word.

Имя файла: `Договор_поставки_ТОО-Альфа_2026-09-07_v3.docx`. Метаданные файла (автор, дата, версия) — заполняются.

### 1.5 Что сюда переезжает из существующего кода
- `contracts/exporter.py` → удаляется, заменён рендером.
- `law_generator/export.py` (892 строки) → удаляется, заменён рендером.
- `law_generator/templates.py` — тексты промптов остаются, переезжают в паспорт типа.
- `LawProject` / `LawProjectVersion` → мигрируют в `documents` / `document_versions` с `kind = law_project`; старые строки переносятся скриптом.

## 2. Модуль «Договоры»

### 2.1 Исследование: какие договоры бывают

Основа классификации — Особенная часть Гражданского кодекса РК (главы 25–47) плюс отдельные кодексы и законы. Ниже каталог, который предлагаю реализовать, с пометкой очереди.

**Очередь 1 — расширение девяти существующих до полноценных паспортов** (ГК РК, ТК РК):
| Тип | Правовая основа | Что добавить к нынешнему шаблону |
|---|---|---|
| Купля-продажа | ГК РК гл. 25 §1 | подвиды: недвижимость (ст. 428–435, госрегистрация), транспорт, доля в ТОО |
| Поставка | ГК РК гл. 25 §3 | спецификация как приложение (таблица → XLSX), график поставок, качество/приёмка по ст. 428, 436 |
| Аренда | ГК РК гл. 29 | подвиды: жилое помещение, нежилое, транспорт, земля (Земельный кодекс), лизинг (Закон «О финансовом лизинге») |
| Возмездное оказание услуг | ГК РК гл. 33 | акт оказанных услуг как приложение |
| Подряд | ГК РК гл. 32 | строительный (§3, смета, график, гарантийный срок), бытовой, проектно-изыскательские |
| Займ | ГК РК гл. 36 | график платежей (таблица), проценты по ст. 718, обеспечение |
| Трудовой | ТК РК ст. 28 (обязательные условия!), 33 | срок, испытательный, режим, отпуск, дистанционная работа (гл. 12-1), ГПХ как отдельный тип |
| Конфиденциальность (NDA) | ГК РК ст. 126, Закон «О коммерческой тайне» | одно- и двусторонний, срок, перечень сведений |
| Агентский | **нет отдельной главы в ГК РК** | пометить как смешанный на базе поручения (гл. 41) и комиссии (гл. 43); честно сказать это пользователю в паспорте |

**Очередь 2 — новые типы с высокой востребованностью:**
- Договор ГПХ (возмездные услуги с физлицом, налоговые оговорки, отличие от трудового по ст. 27 ТК)
- Дополнительное соглашение к любому договору (берёт исходный договор из библиотеки)
- Соглашение о расторжении
- Акт приёма-передачи / акт оказанных услуг / акт выполненных работ (приложения, генерируются к родительскому договору)
- Претензия (досудебная, со ссылкой на пункты договора — генерируется **из** существующего договора)
- Поручительство и гарантия (гл. 22 §4), залог (§3, Закон «Об ипотеке»)
- Лицензионный договор и отчуждение исключительного права (ГК РК ст. 965–966, Закон «Об авторском праве»)
- Хранение (гл. 39), перевозка и транспортная экспедиция (гл. 34–35)
- Комиссия (гл. 43), поручение (гл. 41), доверительное управление (гл. 44)
- Франчайзинг — комплексная предпринимательская лицензия (гл. 45)
- Простое товарищество / совместная деятельность (гл. 12)
- Дистрибьюторский (смешанный: поставка + агентские условия)
- Дарение (гл. 27), мена (гл. 26)

**Очередь 3 — специальные:**
- Учредительный договор ТОО (Закон «О ТОО»), корпоративный договор
- Брачный договор (Кодекс «О браке и семье», гл. 7, нотариальная форма)
- Договор с самозанятым / ИП на упрощёнке (налоговые оговорки)
- Опцион, предварительный договор (ст. 390), соглашение о задатке (ст. 337)
- Договор об оказании юридических услуг (для самих юристов), договор об оказании медицинских / образовательных услуг

**Паспорт типа** — единый формат, из которого строятся форма, промпт и проверка:
```
id, name (ru/kz/en), family (продажа|аренда|работы|услуги|финансы|труд|ИС|корпоративное|семейное)
legal_basis[]: [{ act: "ГК РК", articles: "406–500" }]
form: письменная | нотариальная | госрегистрация
essential_terms[]: условия, без которых договор не заключён (ст. 393 ГК РК) — движок ПРОВЕРЯЕТ их наличие
fields[]: как сейчас, плюс group, hint, validation (ИИН 12 цифр, БИН, дата)
sections[]: { title, required, guidance }  — guidance = что должно быть в разделе
annexes[]: какие приложения бывают (спецификация, акт, график)
risks[]: типичные риски для стороны 1 / стороны 2 — показываются в предпросмотре
```

Паспорты — это данные (YAML в `docengine/catalog/contracts/*.yaml`), не код. Юрист может править их без программиста. Каждый паспорт **должен пройти проверку практикующим юристом** до релиза: ссылки на статьи в текущем коде не проверялись, и я не могу это гарантировать сам.

### 2.2 Экраны

**Каталог** (`/contracts`): типы группами по семействам, фильтр «я — заказчик / исполнитель / арендодатель…», поиск. У каждого типа: правовая основа, форма, срок генерации, «на чём основан». Отдельно вкладка **«Проверить договор»** (существующий анализатор).

**Конструктор** (`/contracts/new/:type`): слева форма по группам (Стороны → Предмет → Условия → Дополнительно), справа **живой лист A4**. Реквизиты, стороны, город, дата подставляются в предпросмотр **мгновенно без LLM** — по шаблону-скелету типа. Кнопка «Составить» запускает генерацию содержательных разделов; они появляются в листе по мере готовности (SSE). Валидация полей до отправки: ИИН/БИН по контрольной сумме, даты, суммы.

**Документ** (`/contracts/:id`): лист по центру с оглавлением слева; справа панель **«Изменить»** — чат над документом (п. 1.3) с быстрыми командами и историей версий. Каждый пункт кликабелен: «править вручную», «попросить переписать этот пункт», «объяснить, зачем он». Сверху: Скачать ▾ (DOCX / PDF / XLSX для приложений), Сохранить в дело, Проверить как сторона 1 / 2 (запускает анализатор на собственном тексте), Создать приложение ▾ (акт, доп. соглашение, претензия).

**Мои договоры** (`/contracts/mine`): реестр таблицей, как в дизайн-системе: тип, стороны, дата, версия, статус (черновик / согласован / подписан), дело.

### 2.3 Качество генерации
- RAG-контекст берётся не по названию типа, а **по каждому разделу**: для «Ответственность» ищем нормы о неустойке, для «Расторжение» — ст. 401–404 ГК.
- Ссылки на статьи в пунктах выдаются как `refs[]` и рендерятся правовой координатой (`.cite`), по клику открывается норма из корпуса. Ссылка, которой нет в корпусе, помечается и **не** выдаётся за проверенную.
- Проверка существенных условий после генерации: недостающие показываются жёлтой плашкой в листе с кнопкой «дополнить».
- Двуязычный договор (ru + kz в две колонки) — стандартная практика в РК; делается как рендер-режим, перевод — операцией над деревом с сохранением нумерации.

## 3. Модуль «Законопроекты»

### 3.1 Что сохраняем
Состав пакета из 13 разделов правильный и соответствует практике сопровождения законопроектов (пояснительная записка, сравнительная таблица, финансово-экономическое обоснование, АРВ, антикоррупционная экспертиза). Валидатор и подсказки по полям — оставляем, подключаем к фронту.

Отдельно проверить по Закону РК «О правовых актах» и Регламенту Мажилиса, что структура текста закона (статьи → пункты → подпункты, заключительные и переходные положения) и состав сопроводительных документов актуальны. Это проверка, а не переписывание.

### 3.2 Что меняем
- Пересадка на документный движок: `kind = law_project`, разделы → `sections[]`, таблицы → `tables[]`.
- **Генерация в фоне с прогрессом** по разделам вместо одного 13-шагового запроса. Разделы независимы друг от друга по данным, поэтому часть можно генерировать параллельно (аннотация, глоссарий, прогноз) при наличии квоты у провайдера.
- **Итерации**: перегенерировать один раздел с уточнением («усилить финансовое обоснование, добавить расчёт на 3 года»), не трогая остальные. Та же панель «Изменить», что у договоров.
- **Экспорт**: DOCX всего пакета (каждый раздел с новой страницы, оглавление Word), PDF, **XLSX** для табличных разделов (сравнительная таблица «было / стало / обоснование», финансовое обоснование по годам, глоссарий), JSON и Akoma Ntoso XML — оставляем как есть, они уже работают.
- Мастер сбора данных: пошаговый, с сохранением сессии (модель уже есть), подсказками валидатора и оценкой полноты. Возможность **начать с загруженного документа** (концепция, поручение) — движок вытаскивает из него цели, предмет, инициатора.

### 3.3 Экраны
**Реестр** (`/laws`): таблица проектов со статусом, датой, версией. **Мастер** (`/laws/new`): 4 шага (Реквизиты → Цели и предмет → Регулирование → Проверка), справа — «что войдёт в пакет» и оценка полноты. **Документ** (`/laws/:id`): оглавление по 13 разделам слева, лист по центру, панель «Изменить» и версии справа, Скачать ▾.

## 4. Модуль «Документы» (рабочее место)

Спецификация есть, план реализации — по ней. Здесь только связки с остальным и приоритеты.

### 4.1 Порядок внутри модуля
1. Таблицы `matters`, `user_documents`, `user_document_versions`, `user_document_chunks` + хранилище файлов.
2. Загрузка PDF / DOCX / изображений с фоновой индексацией и прогрессом (та же очередь, что у генерации).
3. Библиотека и дела на реальных данных, поиск по библиотеке.
4. Диалог с документом (двойное извлечение, ссылки «пункт → норма» — как в спецификации).

### 4.2 Связки, ради которых всё и делается
- Сгенерированный договор или законопроект **сохраняется как документ библиотеки** в выбранном деле, со своими версиями. Один список «всё по делу N».
- Загруженный чужой договор → «Проверить» (анализатор) → «Составить протокол разногласий» или «Претензию» (генератор из существующего документа).
- Чат-консультант получает переключатель «искать по моей библиотеке / по законодательству / по обоим» (уже описано в спецификации, §6).

## 5. Платформенные доработки (нужны всем модулям)

1. **SSE-стриминг** ответов и прогресса: включить `stream=True` в `llm_providers`, один общий эндпоинт `/api/jobs/<id>/events`.
2. **Очередь фоновых задач** на PostgreSQL: генерация, индексация, экспорт больших пакетов. Один воркер-процесс, запускается рядом с приложением.
3. **Логирование**: `logging` с JSON-форматом вместо 75 `print()`; каждой задаче — `job_id` в логах.
4. **Ограничение частоты**: генерация договора — дорогая операция; лимит по пользователю (например 20 генераций в час) через `Flask-Limiter` на том же PostgreSQL.
5. **Тесты**: минимум по спецификации (3) плюс на движок: применение `ops` к дереву, проверка существенных условий, рендер DOCX/PDF/XLSX без исключений, миграция старых `LawProject`.
6. **Персональные данные**: в договорах есть ИИН и адреса физлиц. Шифрование поля `tree` на уровне БД не делаем сейчас, но: доступ строго по `owner_id`, логи не содержат содержимого документов, экспортные файлы не оседают на диске (отдаём из памяти, как сейчас в `export_contract`).

## 6. Последовательность работ

Оценка при работе с субагентами и при том, что визуальная часть фронта уже стоит на дизайн-системе. Каждый шаг заканчивается работающим экраном, а не «половиной модели».

**Шаг 1 (≈ неделя). Движок + договоры на девяти типах.**
Схема `documents / document_versions / document_turns`, паспорта девяти типов в YAML, JSON-генерация по разделам, рендер HTML → DOCX / PDF, экраны Каталог → Конструктор → Документ на живом API. Скачивание работает. Итераций пока нет.

**Шаг 2 (≈ неделя). Итерации и версии.**
`document_turns` с операциями над деревом, панель «Изменить», быстрые команды, ручная правка пункта, история версий с диффом и откатом. Проверка существенных условий. Анализатор в новом UI. Реестр «Мои договоры».

**Шаг 3 (≈ неделя). Каталог договоров, очередь 2.**
Пятнадцать новых паспортов, приложения (акт, спецификация → XLSX, доп. соглашение, претензия из существующего договора), двуязычный рендер. Юридическая вычитка паспортов — параллельно, силами юриста.

**Шаг 4 (≈ неделя). Законопроекты.**
Миграция на движок, фоновая генерация с прогрессом, перегенерация раздела, DOCX / PDF / XLSX, мастер на сессиях, три экрана.

**Шаг 5 (≈ 1,5 недели). Документы.**
По спецификации рабочего места: хранилище, загрузка, индексация, библиотека и дела, диалог с документом. Связки с договорами и законопроектами.

**Шаг 6 (≈ 3 дня). Платформа и хвосты.**
Логирование, лимиты, тесты, удаление 15 Jinja-шаблонов и старых экспортеров, пререндер публичных страниц.

Итого около шести недель. Шаги 1–2 дают то, о чём вы просили в первую очередь: нормальный договор, скачивание в Word/PDF и правка промптом.

## 7. Открытые вопросы (нужны ваши решения)

1. **Юридическая вычитка паспортов.** Кто проверяет статьи и существенные условия? Без этого продукт выдаёт «правовую основу», за которую никто не отвечает.
2. **Порядок модулей.** Предложен: договоры → законопроекты → документы. Если библиотека нужна раньше договоров, шаги 5 и 1–2 меняются местами; движок всё равно первый.
3. **Двуязычный договор** (ru + kz в две колонки): делать в шаге 3 или отложить?
4. **Хранение файлов** для документов: локальная папка на сервере или S3-совместимое хранилище (в спецификации выбран локальный диск)?
5. **Очередь три** каталога (учредительный, брачный, корпоративный): нужна ли в первом релизе или это следующий этап?

- Автоматическую отправку контрагенту, согласование по маршруту.
